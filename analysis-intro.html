تحلیل و بهینه‌سازی کد پایتون؛ از بررسی تا ارزیابی

در این مقاله یک الگوریتم مشخص را بررسی می‌کنیم، نقاط ضعف احتمالی آن را توضیح می‌دهیم و با استفاده از ساختار داده مناسب، نسخه‌ای با پیچیدگی زمانی بهتر می‌سازیم. سپس صحت و عملکرد دو نسخه را مقایسه می‌کنیم.

رفتن به تحلیل‌گر کد

۱. مقدمه

بهینه‌سازی نرم‌افزار فرایندی برای بهبود عملکرد برنامه، کاهش مصرف منابع یا افزایش خوانایی و نگهداشت‌پذیری کد است. با این حال، هر تغییر ظاهری یا کوتاه‌تر شدن کد لزوماً به معنای بهینه‌تر شدن آن نیست.

یک بهینه‌سازی معتبر باید رفتار مورد انتظار برنامه را حفظ کند. بنابراین، علاوه بر تحلیل پیچیدگی، باید آزمون‌های صحت و اندازه‌گیری عملکرد نیز انجام شوند.

۲. تعریف مسئله

دو فهرست به نام‌های list_a و list_b داریم. هدف، یافتن عناصری است که در هر دو فهرست وجود دارند؛ هر عنصر فقط یک بار در خروجی قرار می‌گیرد و ترتیب اولین حضور آن در فهرست اول حفظ می‌شود. 

list_a = [1, 2, 3, 2, 4, 5]
list_b = [2, 4, 5, 6]

# Expected output:
[2, 4, 5]

حفظ ترتیب مهم است؛ زیرا استفاده از یک مجموعه برای ساخت مستقیم خروجی می‌تواند ترتیب مورد انتظار را تغییر دهد.

۳. پیاده‌سازی اولیه

def find_common_elements(list_a, list_b):
    result = []

    for item in list_a:
        if item in list_b:
            if item not in result:
                result.append(item)

    return result

تحلیل عملکرد

برای هر عنصر از list_a، عبارت item in list_b ممکن است تمام عناصر فهرست دوم را بررسی کند. این عملیات در بدترین حالت O(m) زمان می‌برد.

بررسی item not in result نیز در بدترین حالت متناسب با تعداد عناصر خروجی، یعنی حداکثر O(n) زمان نیاز دارد.

اگر n طول فهرست اول و m طول فهرست دوم باشد، کران بالای زمانی این پیاده‌سازی O(nm + n²) است. حافظه اضافی برای فهرست نتیجه حداکثر O(n) است.

۴. نسخه بهینه‌شده

def find_common_elements_optimized(list_a, list_b):
    set_b = set(list_b)
    seen = set()
    result = []

    for item in list_a:
        if item in set_b and item not in seen:
            result.append(item)
            seen.add(item)

    return result

چرا این نسخه سریع‌تر است؟

  • مجموعه set_b امکان بررسی عضویت را با زمان مورد انتظار O(1) فراهم می‌کند.
  • مجموعه seen از تکرار عناصر خروجی جلوگیری می‌کند.
  • فهرست result ترتیب اولین حضور عناصر را حفظ می‌کند.

ساخت set_b به‌طور متوسط O(m) زمان نیاز دارد. سپس حلقه روی فهرست اول با بررسی‌های عضویت مورد انتظار O(1) برای هر عنصر اجرا می‌شود.

در نتیجه، پیچیدگی زمانی مورد انتظار برابر O(n + m) و پیچیدگی حافظه اضافی O(n + m) است.

این تحلیل برای رفتار معمول جدول هش است. عملکرد بدترین حالت می‌تواند متفاوت باشد. همچنین، عناصر فهرست‌ها باید قابل هش شدن باشند؛ برای مثال، عددها و رشته‌ها معمولاً قابل استفاده‌اند، اما فهرست‌های تو‌در‌تو مستقیماً نمی‌توانند عضو set باشند.

۵. مقایسه دو پیاده‌سازی

ویژگی نسخه اولیه نسخه بهینه‌شده
زمان مورد انتظار O(nm + n²) O(n + m)
حافظه اضافی O(n) O(n + m)
حفظ ترتیب خروجی بله بله
حذف تکرارها بله بله
نیاز به عناصر قابل هش شدن خیر بله

این جدول نشان می‌دهد نسخه بهینه‌شده در شرایط معمول، رشد زمانی بهتری دارد؛ اما برای این بهبود، حافظه بیشتری مصرف می‌کند. انتخاب مناسب به محدودیت‌های واقعی برنامه بستگی دارد.

۶. آزمون صحت

پیش از مقایسه سرعت، باید بررسی کنیم که هر دو پیاده‌سازی خروجی مورد انتظار را تولید می‌کنند. 

def run_tests():
    cases = [
        ([1, 2, 3], [2, 3, 4], [2, 3]),
        ([1, 1, 2, 2], [1, 2], [1, 2]),
        ([], [1, 2], []),
        ([1, 2], [], []),
        ([5, 4, 3, 2], [2, 3, 5], [5, 3, 2]),
        (["a", "b", "a"], ["a", "c"], ["a"]),
    ]

    for a, b, expected in cases:
        original = find_common_elements(a, b)
        optimized = find_common_elements_optimized(a, b)

        assert original == expected
        assert optimized == expected
        assert original == optimized

    print("All tests passed!")

این آزمون‌ها چند حالت مهم از جمله ورودی خالی، تکرار عناصر، رشته‌ها و ترتیب خروجی را پوشش می‌دهند. موفقیت آن‌ها شواهدی برای صحت این نمونه‌هاست، اما به‌تنهایی اثبات رسمی برای تمام ورودی‌های ممکن نیست.

۷. بنچمارک و اندازه‌گیری زمان اجرا

تحلیل پیچیدگی، رفتار رشد الگوریتم را توصیف می‌کند؛ اما برای مشاهده عملکرد واقعی باید زمان اجرا را اندازه‌گیری کنیم. ماژول استاندارد timeit پایتون برای این کار مناسب است. 

import random
import timeit

random.seed(42)

size = 3000

list_a = [
    random.randint(0, size)
    for _ in range(size)
]

list_b = [
    random.randint(0, size)
    for _ in range(size)
]

# Verify equivalent results first.
assert (
    find_common_elements(list_a, list_b)
    ==
    find_common_elements_optimized(list_a, list_b)
)

original_time = min(
    timeit.repeat(
        lambda: find_common_elements(list_a, list_b),
        repeat=3,
        number=1
    )
)

optimized_time = min(
    timeit.repeat(
        lambda: find_common_elements_optimized(list_a, list_b),
        repeat=3,
        number=1
    )
)

print("Original:", original_time)
print("Optimized:", optimized_time)

if optimized_time > 0:
    print("Speedup:", original_time / optimized_time)

چگونه نتایج را گزارش کنیم؟

زمان‌های واقعی را پس از اجرای کد ثبت کن. برای مقایسه معتبرتر، آزمایش را با اندازه‌های مختلف ورودی تکرار کن و نسخه پایتون، مشخصات محیط اجرا و روش اندازه‌گیری را گزارش بده.

هیچ زمان اجرا یا ضریب سرعتی در این مقاله به‌عنوان نتیجه اندازه‌گیری‌شده اعلام نشده است؛ اعداد واقعی باید از اجرای آزمایش به دست آیند.

۸. محدودیت‌ها

  • نسخه بهینه‌شده برای عناصر قابل هش شدن طراحی شده است.
  • مجموعه‌ها حافظه اضافی مصرف می‌کنند.
  • زمان اجرای واقعی به اندازه و توزیع داده‌ها و محیط اجرا وابسته است.
  • تحلیل پیچیدگی به فرض‌های مشخص درباره عملیات و رفتار ساختار داده‌ها نیاز دارد.
  • ابزارهای تحلیل ایستا ممکن است نتوانند رفتار زمان اجرا را به‌طور کامل پیش‌بینی کنند.

۹. روش‌شناسی پروژه PyOptimize

نسخه فعلی تحلیل‌گر در صفحه اصلی PyOptimize، الگوهای متنی محدودی را در کد ورودی جست‌وجو می‌کند. این بررسی در مرورگر انجام می‌شود و کد پایتون اجرا نمی‌شود.

بنابراین، هشدارهای ابزار باید به‌عنوان پیشنهاد برای بررسی بیشتر در نظر گرفته شوند، نه تشخیص قطعی خطا یا تضمین افزایش سرعت.

برای توسعه‌های بعدی می‌توان از تجزیه‌کننده نحوی AST پایتون، آزمون‌های خودکار و اجرای بنچمارک در محیط کنترل‌شده استفاده کرد. اجرای واقعی کد پایتون از طریق وب نیز به محیط اجرایی مناسب نیاز دارد.

۱۰. نتیجه‌گیری

در این مطالعه، الگوریتم یافتن عناصر مشترک دو فهرست را بررسی کردیم و با استفاده از set، جست‌وجوهای خطی تکراری را کاهش دادیم.

پیچیدگی زمانی مورد انتظار از O(nm + n²) به O(n + m) کاهش یافت. در مقابل، حافظه اضافی بیشتری مصرف شد و محدودیت قابل هش بودن عناصر نیز به وجود آمد.

نتیجه اصلی این است که بهینه‌سازی مؤثر به انتخاب ساختار داده مناسب، حفظ رفتار مورد انتظار، آزمون صحت و ارزیابی عملکرد در شرایط واقعی وابسته است.
