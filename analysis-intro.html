مقدمه‌ای بر تحلیل ایستای کد پایتون

تحلیل ایستا یعنی بررسی کد بدون اجرای آن. در این مطلب می‌بینیم چه چیزهایی را می‌توان از ساختار کد فهمید و کجا باید به اندازه‌گیری واقعی تکیه کرد.

هدف این پروژه

هدف این پروژه ساختن یک ابزار ساده و قابل‌فهم برای پیدا کردن الگوهای کندکننده در کد پایتون است. ابزار کد را بدون اجرا بررسی می‌کند، نقاط مشکوک را با شماره‌ی خط گزارش می‌دهد و پیشنهاد می‌کند چه تغییری بدهی. هدف دوم این است که نشان دهیم چطور بعد از هر تغییر، بهبود واقعی را با اندازه‌گیری تأیید کنی.

تحلیل ایستا چیست؟

کد پایتون را می‌توان به‌صورت یک درخت نحوی (AST) خواند. ماژول ast در کتابخانه‌ی استاندارد این درخت را در اختیارت می‌گذارد. با پیمایش این درخت می‌توان الگوهایی را پیدا کرد که معمولاً کندی ایجاد می‌کنند، مثل:

  • جست‌وجوی in روی لیست داخل حلقه
  • الحاق رشته با += داخل حلقه
  • حلقه‌های تودرتو
  • توابع بازگشتی بدون کش

ابزار این مطلب

اسکریپت analyzer.py همین کار را انجام می‌دهد. برای اجرا:

python analyzer.py your_code.py

خروجی شامل تخمین پیچیدگی هر تابع بر اساس عمق حلقه‌ها و فهرست مشکلات احتمالی با شماره‌ی خط است.

نمونه‌ی عملی

تابعی را در نظر بگیر که کاربرهای ثبت‌شده در لاگ را فیلتر می‌کند. نسخه‌ی اول از in روی لیست و حلقه‌ی تودرتو روی blacklist استفاده می‌کند. با تبدیل ورودی‌ها به set و ساخت یک‌باره‌ی رشته با join، همان خروجی با سرعت بسیار بیشتری به دست می‌آید. در یک بنچ‌مارک با ۵۰۰۰ لاگ و ورودی تصادفی، نسخه‌ی بهینه حدود ۱۷۳ برابر سریع‌تر بود. همچنین فیبوناچی بازگشتی با lru_cache در همان آزمایش حدود ۲۳۰۰ برابر سریع‌تر شد.

این اعداد مربوط به یک ورودی مشخص روی یک ماشین مشخص است. اندازه‌ی بهبود به داده و محیط بستگی دارد، پس برای گزارش دقیق، خودت هم با timeit بسنج.

محدودیت‌های تحلیل ایستا

تحلیلگر ساختاری فقط الگوها را می‌بیند، نه زمان واقعی را. ممکن است حلقه‌ای را گزارش کند که در عمل کوچک است، و ممکن است گلوگاهی را که با الگوهای شناخته‌شده مطابقت ندارد نبیند. مثلاً در نسخه‌ی تست، حلقه‌ی تودرتوی با عمق ۲ روی blacklist گزارش نشد. برای تصمیم نهایی باید اندازه‌گیری کرد.

مثال کامل: تحلیل و بهینه‌سازی

کد زیر نسخه‌ی اول است. ابتدا آن را با analyzer.py بررسی می‌کنیم:

def find_common_users(logs, blacklist, allowed):
    result = []
    for log in logs:
        if log["user"] not in result:
            for b in blacklist:
                if b == log["user"]:
                    break
            else:
                if log["user"] in allowed:
                    result.append(log["user"])
    report = ""
    for r in result:
        report += f"{r}\n"
    return report
$ python analyzer.py slow_code.py
  find_common_users         O(n²)
  خط 4: جست‌وجوی `in` داخل حلقه روی result
  خط 9: جست‌وجوی `in` داخل حلقه روی allowed
  خط 13: الحاق رشته با += داخل حلقه

تحلیلگر سه مشکل را پیدا کرد. حلقه‌ی تودرتو روی blacklist هم وجود دارد که در گزارش نیامد، پس خروجی تحلیلگر کامل نیست.

نسخه‌ی بهینه:

def find_common_users(logs, blacklist, allowed):
    blacklist_set = set(blacklist)
    allowed_set = set(allowed)
    seen = set()
    result = []
    for log in logs:
        user = log["user"]
        if user in seen or user in blacklist_set:
            continue
        if user in allowed_set:
            seen.add(user)
            result.append(user)
    return "".join(f"{r}\n" for r in result)

تغییرات: جست‌وجو روی set انجام می‌شود (O(1))، حلقه‌ی داخلی روی blacklist حذف شده، و رشته‌ی گزارش یک‌باره ساخته می‌شود.

برای اندازه‌گیری، هر دو نسخه را با timeit روی همان ورودی اجرا کن. در بنچ‌مارک من با ۵۰۰۰ لاگ، نسخه‌ی کند حدود ۱۱۰ میلی‌ثانیه و نسخه‌ی بهینه حدود ۰٫۶ میلی‌ثانیه طول کشید.

جمع‌بندی

تحلیل ایستا برای پیدا کردن نقاط مشکوک خوب است. تصمیم درباره‌ی بهینه‌سازی را باید بر اساس اندازه‌گیری گرفت.
